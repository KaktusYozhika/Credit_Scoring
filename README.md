# Практика 4. Кредитный скоринг (группа 7)

Проект по дисциплине «Методология проектирования интеллектуальных платформ».

Группа БИВТ-23-АЭ-1, команда 7: Панютищева Екатерина, Кривоножкина Александра, Лаптева Екатерина.

Мы разработали сервис, который по кредитным характеристикам заёмщика оценивает риск серьёзной просрочки (90 дней и более) в течение следующих двух лет. Проект продолжает практические работы 1-3: мы используем датасет **Give Me Some Credit** и логистическую регрессию, обученную по подходу из практики 3.

Сервис помогает определить заявки, которые стоит направить на дополнительную проверку кредитному специалисту. Прогноз модели не означает автоматического отказа в кредите. Это учебный прототип, его вероятности не проходили отдельную проверку калибровки для реального банковского применения.

## Структура проекта

| Файл или папка | Назначение |
|---|---|

| `artifacts/versions/v1.0.0/` | Текущая версия, порог 0.55 |
| `artifacts/versions/v0.9.0/` | Предыдущая версия, порог 0.50 |

| `example_request.json` | Пример заявки для запроса `/predict` |

В каждой папке версии модели находятся `model.joblib` (полный Pipeline), `meta.json` (версия, данные, метрики) и `etalon.json` (пять эталонных предсказаний).

## Данные

Мы использовали обучающую часть датасета **Give Me Some Credit**: 150 000 записей, 10 признаков и целевую переменную `SeriousDlqin2yrs`.

- `SeriousDlqin2yrs = 1` - у заёмщика была серьёзная просрочка в течение двух лет.
- `SeriousDlqin2yrs = 0` - серьёзной просрочки не было.

Данные доступны на [странице соревнования Kaggle](https://www.kaggle.com/competitions/give-me-some-credit/data). Для их скачивания может потребоваться вход в аккаунт и принятие правил соревнования. Нужно скачать архив и поместить файл **`cs-training.csv`** в папку **`data/`** рядом с `data/README.md`.

Сам CSV не включён в Git-репозиторий, так как его использование и распространение регулируются правилами соревнования. При этом уже сохранённые артефакты моделей находятся в папке `artifacts/versions/`, поэтому сервис можно запустить без повторного обучения.

## Обучение модели

Для локальной работы рекомендуется Python 3.11. Команды выполняются из корня проекта, где находится `train.py`.

Создать виртуальное окружение:

```bash
python -m venv .venv
```

Активировать его в Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Для Linux или macOS:

```bash
source .venv/bin/activate
```

Установить зависимости и запустить обучение:

```bash
python -m pip install -r requirements.txt
python train.py
```

Перед обучением скрипт удаляет служебный индекс и 609 полных совпадений записей без него. Затем данные разделяются на обучение (70%), валидацию (15%) и отложенную тестовую часть (15%) с сохранением доли целевого класса (`random_state=42`).

Используется `Pipeline` из `SimpleImputer` (медиана и индикаторы пропусков), `StandardScaler` и `LogisticRegression`. Предобработка обучается только на обучающей выборке. Основная метрика - PR-AUC (Average Precision), потому что серьёзная просрочка встречается примерно у 6,68% заёмщиков.

Результаты на валидационной выборке:

| Вариант | PR-AUC (AP) | Precision | Recall | Доля заявок на дополнительную проверку |
|---|---:|---:|---:|---:|
| Базлайн: правило по прежним просрочкам 90+ дней | 0.19134 | - | - | - |
| Логистическая регрессия, порог 0.55 | 0.33065 | 0.26385 | 0.53298 | 0.13530 |
| Та же модель, порог 0.50 | 0.33065 | 0.19553 | 0.64091 | 0.21955 |

При пороге 0.55 модель направляет на дополнительную проверку около 13,5% заявок и выявляет около 53,3% случаев серьёзной просрочки. Порог 0.50 даёт более высокий Recall, но увеличивает количество заявок для проверки. Тестовая часть не использовалась при подборе порога.

## Запуск сервиса

Запустить API локально:

```bash
python -m uvicorn app.main:app --host 127.0.0.1 --port 8077
```

После запуска доступны:

- `GET /health` - состояние сервиса и версия загруженной модели;
- `GET /model-info` - сведения о модели, данных и метриках;
- `POST /predict` - вероятность серьёзной просрочки и результат сравнения с порогом;
- `GET /docs` - интерактивная документация API.

Документация в браузере: http://127.0.0.1:8077/docs

## Проверка запросов

Проверить состояние сервиса можно по адресу http://127.0.0.1:8077/health или через PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:8077/model-info
```

Отправить тестовую заявку в `/predict` (PowerShell, из корня проекта):

```powershell
$body = Get-Content -Raw -Encoding UTF8 example_request.json
Invoke-RestMethod -Uri http://127.0.0.1:8077/predict -Method Post -ContentType 'application/json' -Body $body
```

В ответе будут поля `probability`, `predicted_class`, `threshold`, `model_version` и `recommendation`. Значение `predicted_class = 1` означает, что заявку рекомендуется направить на дополнительную проверку. Значение `0` означает обычное рассмотрение.

Для некорректного запроса API возвращает HTTP 422. Например, ошибка возникнет при `age = 0`, отсутствии обязательного признака или значении `NumberOfTimes90DaysLate = 98`. Поля `MonthlyIncome` и `NumberOfDependents` можно не указывать, так как пропуски по ним обрабатываются в Pipeline.

## Автоматические тесты

Запустить все тесты одной командой:

```bash
python -m unittest discover -s tests -v
```

Тесты проверяют загрузку моделей и метаданных, совпадение пяти эталонных предсказаний, работу `/health`, `/model-info` и `/predict`, ошибки 422 и переключение между версиями. При локальной проверке прошло **13 из 13 тестов**.

## Docker: сборка и запуск

В корне проекта, где находится `Dockerfile`, выполнить:

```bash
docker build --build-arg MODEL_VERSION=v1.0.0 -t credit-scoring:1.0.0 .
docker run --rm -p 8077:8077 --name credit-scoring credit-scoring:1.0.0
```

После запуска контейнера можно открыть http://127.0.0.1:8077/health и http://127.0.0.1:8077/model-info. Проверка `/predict` выполняется тем же запросом, что и для локального сервиса. При одинаковой версии модели ответы должны совпадать.

Docker-образ использует сохранённый Pipeline из `artifacts/versions/`, поэтому исходный CSV для запуска контейнера не требуется.

## Откат на предыдущую версию

В проекте сохранены две версии одной обученной модели:

- `v1.0.0` - текущая конфигурация с порогом 0.55;
- `v0.9.0` - предыдущая конфигурация с порогом 0.50.

Здесь откат показывает возврат к предыдущей конфигурации порога. Сам обученный Pipeline у обеих версий одинаковый.

Остановить текущий контейнер (`Ctrl+C` или `docker stop credit-scoring`), затем собрать и запустить предыдущую версию:

```bash
docker build --build-arg MODEL_VERSION=v0.9.0 -t credit-scoring:0.9.0 .
docker run --rm -p 8077:8077 --name credit-scoring credit-scoring:0.9.0
```

При запросе `/model-info` версия изменится на `v0.9.0`, а порог станет равен `0.5`. Для проверки можно отправить данные из `rollback_example.json`: на версии `v0.9.0` заявка получит класс `1`, а на `v1.0.0` - класс `0`.

Чтобы вернуться к текущей версии, нужно остановить контейнер и запустить образ `credit-scoring:1.0.0`:

```bash
docker run --rm -p 8077:8077 --name credit-scoring credit-scoring:1.0.0
```

Без Docker предыдущую версию можно запустить в PowerShell:

```powershell
$env:MODEL_VERSION='v0.9.0'
python -m uvicorn app.main:app --host 127.0.0.1 --port 8077
```

В Linux/macOS:

```bash
MODEL_VERSION=v0.9.0 python -m uvicorn app.main:app --host 127.0.0.1 --port 8077
```

## Ограничения

В датасете нет дат заявок и идентификаторов заёмщиков, поэтому нельзя проверить, относятся ли совпадающие записи к одним людям, и оценить качество модели на более поздних данных. У признаков `MonthlyIncome` и `NumberOfDependents` есть пропуски. Значения 96-98 в счётчиках просрочек требуют отдельного изучения, поэтому сервис не принимает такие значения во входном запросе.

Модель предназначена для учебной демонстрации. Для использования в реальной кредитной организации понадобятся проверка актуальности данных, калибровка вероятностей и дополнительная оценка качества на новых заявках.
